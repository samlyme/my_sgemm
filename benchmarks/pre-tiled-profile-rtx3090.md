# Pre-tiled kernel profile: RTX 3090

Profiled on an NVIDIA GeForce RTX 3090 (SM 8.6, 24 GiB) with driver 595.99.02 and Nsight Compute 2025.2.1. The workload is `M=N=K=2048` with row-major matrices.

## Standalone performance

These timings were collected sequentially, without a profiler:

| Kernel | Time | Performance |
|---|---:|---:|
| `row-strip` | 13.247 ms | 1,296.9 GFLOP/s |
| `col-strip` | 56.106 ms | 306.2 GFLOP/s |
| `naive` (32x32 block) | 7.299 ms | 2,353.7 GFLOP/s |

## Memory profile

Nsight Compute replays kernels to collect counters, so its durations are slower than the standalone timings. Traffic and utilization figures below come from a single profiled kernel launch.

| Metric | `row-strip` | `col-strip` | `naive` |
|---|---:|---:|---:|
| Profiled duration | 16.34 ms | 79.89 ms | 9.89 ms |
| DRAM read traffic | 12.50 GB | 212.43 MB | 914.12 MB |
| DRAM write traffic | 18.72 MB | 18.81 MB | 18.60 MB |
| DRAM bandwidth | 766.04 GB/s | 2.89 GB/s | 94.32 GB/s |
| DRAM utilization | 84.06% | 0.32% | 10.35% |
| L1 global-load traffic | 42.97 GB | 283.46 GB | 42.97 GB |
| L1 global-load hit rate | 20.64% | 84.10% | 94.96% |
| L1/TEX throughput utilization | 57.65% | 97.63% | 96.14% |
| L2 traffic | 34.12 GB | 45.40 GB | 2.19 GB |
| L2 sector hit rate | 63.25% | 99.50% | 58.41% |
| L2 throughput utilization | 96.43% | 26.25% | 10.22% |
| Achieved occupancy | 95.44% | 98.13% | 66.51% |

`GB` and `GB/s` are the decimal units reported by Nsight Compute.

## Interpretation

### Row strip: DRAM/L2 bandwidth bound

A warp computes adjacent columns of one output row. Its `B` accesses are contiguous and its `A` access is a warp-wide broadcast, so the requests are well coalesced. However, different blocks compute different row strips and do not explicitly retain `B`. Most reuse must be discovered across independently scheduled blocks.

The low L1 hit rate, 12.50 GB of DRAM reads, 84% DRAM utilization, and 96% L2 throughput utilization show that this kernel is close to the off-chip/cache bandwidth roof. Its 100% theoretical and 95% achieved occupancy are not enough to overcome the amount of data movement.

### Column strip: uncoalesced and L1/TEX-pipeline bound

A warp computes adjacent rows of one output column. `B` becomes a broadcast, but the 32 `A` addresses are separated by an entire row stride. Nsight Compute reports about 7.52 billion excessive sectors, approximately 85% of the 8.87 billion sectors generated by the kernel.

This creates 283.46 GB of L1 global-load traffic, over 6.5 times the traffic of the coalesced kernels. The data is frequently found in cache—84% L1 and about 99.5% L2 hit rates—so DRAM itself is only 0.32% utilized. Performance is instead limited by issuing and processing excessive sectors through the L1/TEX path, which reaches 97.63% utilization.

This is an important distinction: poor coalescing does not necessarily imply high DRAM bandwidth. Cached, uncoalesced accesses can saturate an on-chip request/data path while barely using DRAM.

### Naive 32x32 block: implicit cache tiling

CUDA linearizes the 32x32 block with `threadIdx.x` varying fastest, so every warp computes one horizontal row. Each warp therefore has the same favorable access pattern as the row-strip kernel.

The difference is temporal locality. The block's 32 warps compute adjacent output rows and request the same segment of `B` for each inner-loop iteration. L1 captures that reuse: its hit rate rises from 20.64% for row strips to 94.96%. Consequently, DRAM reads fall from 12.50 GB to 914 MB and DRAM utilization falls to 10.35%.

The 1,024-thread block permits only one block, or 32 warps, per SM. That limits theoretical occupancy to 66.67%, compared with 100% for the strip kernels. Despite the lower occupancy, cache locality makes this kernel approximately 1.8 times faster than row strips and 7.7 times faster than column strips.

## Reproduction

Standalone timings:

```bash
for kernel in row-strip col-strip naive; do
  ./build/sgemm_bench --kernel "$kernel" \
    --m 2048 --n 2048 --k 2048 --iters 10
done
```

The profiler executable in this environment is `../SGEMM_CUDA/.ncu/ncu`. Skip the correctness launch and five warmup launches, then profile one timed launch:

```bash
../SGEMM_CUDA/.ncu/ncu \
  --set detailed \
  --launch-skip 6 \
  --launch-count 1 \
  ./build/sgemm_bench --kernel naive \
    --m 2048 --n 2048 --k 2048 --iters 1
```

Replace `naive` with `row-strip` or `col-strip` for the other kernels.
